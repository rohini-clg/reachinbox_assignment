## Remaining finding

- **High: GHSA-7589-6fvf-x4pw:** `effect@3.20.0` is affected (`<=3.22.0`) by ReDoS in `Schema.TemplateLiteral` compiled regex. It is pulled by `@prisma/config@7.10.1` and the `prisma@7.10.1` CLI, which is declared in backend `devDependencies`; the application server does not import the Prisma CLI. npm's proposed fix is `prisma@6.12.0`, a major downgrade from Prisma 7, so it was not applied. The audit command still reports these three dependency-graph records even with `--omit=dev` because the optional Prisma peer is represented in the lock graph; this is not evidence that the CLI is bundled into the deployed server. Reassess on a Prisma release that updates its pinned Effect dependency, or validate an upstream-supported override before adopting one. No override or `--force` was used.
- The application runtime's direct vulnerable dependencies were remediated: backend `bullmq` and `nodemailer`; frontend `axios`, `next`, and `next-auth`. The Nodemailer API use (`createTransport`/`sendMail` with ordinary message fields) was checked against its v10 CommonJS exports and bundled TypeScript declarations; Node 22 meets its `>=20` engine requirement. SMTP sending was not exercised because credentials are absent.
- Current backend `npm audit --omit=dev` still reports the same 3 package-graph records for the Effect/Prisma tooling chain; frontend production audit is clean. Do not describe the complete repository audit as vulnerability-free.
